# Eugene Work — архитектура и план интеграции

Версия документа: 0.1  
Статус: проектное решение для MVP, не спецификация уже работающего облачного backend.

## 1. Продуктовая модель

Eugene Work — рабочее пространство внутри экосистемы Eugene / Symbiont. Пользователь входит в один кабинет и работает с объектами нескольких типов:

- календарные события;
- заметки;
- текстовые документы;
- таблицы;
- презентации;
- файлы и вложения.

Это не набор независимых приложений с отдельными профилями. У объектов общий идентификатор владельца, единая навигация, поиск, права доступа, история изменений и механизм резервного копирования.

## 2. Синтез существующих решений

Цель — объединить проверенные компоненты, а не переписывать зрелые редакторы.

| Область | Кандидаты для оценки | Принцип выбора |
|---|---|---|
| Текстовый редактор | Tiptap / ProseMirror | Расширяемая схема документа, плагины, сериализация |
| Таблицы | Univer; при потребности в форматах Office — ONLYOFFICE Docs или Collabora Online | Формулы, импорт/экспорт, диапазоны, совместимость, лицензия |
| Презентации | Проверить возможности выбранного офисного движка; иначе отдельный слайдовый редактор | Экспорт PPTX/PDF, темы, заметки докладчика, доступность |
| Календарь | FullCalendar либо собственный лёгкий интерфейс | Повторяющиеся события, часовые пояса, доступность, мобильная навигация |
| Совместное редактирование | Yjs/CRDT или функции встроенного движка | Сначала определить семантику конфликтов и хранение истории |
| Файлы | S3-совместимое объектное хранилище | Подписанные URL, версии, квоты, резервное копирование |
| Backend | PostgreSQL + API; объектное хранилище для вложений | Транзакции, контроль доступа, миграции и наблюдаемость |

Таблица — shortlist для технического исследования, не утверждение о совместимости или текущем лицензионном статусе. До внедрения нужно проверить актуальные лицензии, доступность self-hosted-развёртывания, коммерческие условия, ограничения бесплатных редакций, формат данных, миграцию и поддержку мобильных устройств.

## 3. Архитектура

```text
Eugene Work UI
    |
    v
Workspace Domain
    |-- Documents
    |-- Notes
    |-- Spreadsheets
    |-- Presentations
    |-- Calendar Events
    |-- Files
    |
    v
Application API
    |-- Identity & Sessions
    |-- Authorization
    |-- Search
    |-- Revision History
    |-- Sync / Conflict Resolution
    |
    +--> PostgreSQL (metadata, permissions, revisions)
    +--> Object Storage (attachments, exports)
    +--> Queue / Workers (thumbnails, indexing, notifications)
    +--> Editor engines / external connectors
```

### Границы ответственности

- **UI** отображает данные и передаёт пользовательские действия.
- **Domain layer** задаёт типы объектов, валидацию и бизнес-правила.
- **API** проверяет каждое действие и право доступа на сервере.
- **Database** хранит метаданные, права и историю.
- **Object storage** хранит содержимое файлов и экспортов.
- **Sync engine** управляет версиями, очередью офлайн-изменений и конфликтами.
- **Editor adapters** скрывают детали конкретного редакторного движка.

Нельзя считать скрытый интерфейс или идентификатор объекта защитой. Все права проверяются сервером.

## 4. Унифицированная модель объекта

Минимальный серверный envelope:

```json
{
  "id": "uuid",
  "workspace_id": "uuid",
  "type": "note | document | spreadsheet | presentation | event | file",
  "title": "string",
  "created_by": "user-id",
  "created_at": "ISO-8601 UTC",
  "updated_at": "ISO-8601 UTC",
  "version": 1,
  "deleted_at": null,
  "content_ref": "optional storage reference"
}
```

Каждый тип сохраняет собственную схему содержимого. Общий envelope нужен для поиска, сортировки, прав, истории и синхронизации, а не для сведения всех документов к одному формату.

## 5. Синхронизация и автономный режим

Надёжная синхронизация — это не просто периодический POST. Целевая модель:

1. Каждое локальное действие создаёт операцию с уникальным ID.
2. Операция попадает в локальную очередь outbox.
3. Клиент отправляет операции повторно до подтверждения сервера.
4. Сервер обрабатывает повтор операции идемпотентно.
5. Объект имеет версию; сервер сообщает актуальную версию при конфликте.
6. Простые поля можно разрешать по полю/версии; сложный текст и таблицы требуют стратегии на уровне редактора.
7. Удаление фиксируется tombstone-записью, чтобы объект не воскрес после синхронизации старого устройства.
8. Клиент показывает статусы «локально сохранено», «синхронизируется», «синхронизировано» и «конфликт».
9. Политика очистки истории и восстановление из резервной копии тестируются отдельно.

CRDT/OT не устраняют необходимость в аутентификации, авторизации, хранении истории и управлении версиями.

## 6. Безопасность и приватность

- HTTPS везде; secure, HttpOnly, SameSite cookies для веб-сессий при соответствующей архитектуре.
- Проверка доступа на сервере для каждой операции и каждого файла.
- Изоляция данных по workspace и владельцу; негативные тесты на межпользовательский доступ.
- Защита от XSS: санитизация HTML и безопасная схема редактора.
- CSRF-защита, rate limiting, проверка типов/размеров файлов, безопасная обработка импорта.
- Секреты только в серверном хранилище секретов, не в git и не в клиентском JS.
- Резервные копии с тестами восстановления, журнал аудита административных действий.
- Экспорт и удаление пользовательских данных должны быть понятными.
- Шифрование на диске и end-to-end encryption — разные свойства; не заявлять E2EE без корректного управления ключами и проверки реализации.

## 7. Этапы

### Этап A — текущий статический MVP
Навигация, базовые CRUD-операции, локальное сохранение, поиск, CSV и JSON backup. Нет аккаунтов, сервера и синхронизации.

### Этап B — надёжный клиент
IndexedDB, схема и миграции, тесты на восстановление, доступность клавиатурой, импорт/экспорт, автосохранение с индикацией.

### Этап C — серверное ядро
Регистрация/вход, workspace, API, PostgreSQL, объектное хранилище, серверная авторизация, аудит и резервное копирование.

### Этап D — синхронизация
Outbox, идемпотентность, версии, конфликтные состояния, offline-first сценарии и тесты двух устройств.

### Этап E — редакторы
Выбрать и интегрировать офисный движок после сравнительного теста: документы, таблицы, презентации, экспорт, производительность, лицензия, self-hosting.

### Этап F — командная работа
Общий доступ, роли, приглашения, комментарии, история версий, присутствие и совместное редактирование.

### Этап G — production
Мониторинг, алерты, лимиты, миграции, нагрузочные и security-тесты, план реагирования на инциденты.

## 8. Критерии готовности облачного продукта

- Данные доступны после входа с другого устройства.
- Права доступа проверяются на сервере и покрыты негативными тестами.
- Офлайн-изменения не теряются после перезапуска.
- Повторная отправка запроса не создаёт дубликаты.
- Конфликт виден пользователю и не приводит к молчаливой потере данных.
- Резервная копия реально восстанавливается в тестовой среде.
- Есть экспорт данных и понятный путь удаления аккаунта.
- Лицензии всех встроенных компонентов документированы.
- Совместное редактирование проверено несколькими пользователями и устройствами.

## 9. Ограничения текущего прототипа

- `localStorage` не является облачной базой данных и не синхронизируется между устройствами.
- Редактор документа и сетка таблицы — упрощённые MVP-компоненты, не полные аналоги Google Docs/Sheets.
- Презентации пока не экспортируются в PPTX.
- Календарь пока не поддерживает повторения, приглашения и внешние календари.
- Не реализованы аккаунты, серверные права, история версий, шифрование содержимого и совместное редактирование.
- Статический сайт на GitHub Pages может показать UI, но не заменить серверный слой.
